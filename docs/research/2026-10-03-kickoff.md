# ratekit kickoff research (2026-10-03)

Idea: open-source usage metering and rating engine. Java 21, Spring Boot 3, Maven multi-module, Kafka, PostgreSQL, three services (ingest, rating, billing). Learning project: a small usage metering and rating engine.

Provenance: one research subagent, 5 tool calls. Only the OpenMeter GitHub page was opened; everything else comes from search snippets or secondary sources. Treat licenses and languages below as unverified until checked on the primary repo.

## Stack options (trade-offs, no winner yet)

- **Idempotency**: unique `(tenant, event_id)` with `INSERT ... ON CONFLICT DO NOTHING` (simple, table grows, needs retention); Redis SETNX (extra component, consistency gaps); Kafka idempotent producer alone (covers producer retries only).
- **Kafka semantics**: at-least-once plus idempotent consumer is the pragmatic default. Kafka transactions cover Kafka-to-Kafka only, not a Postgres write. Outbox: polling with `SKIP LOCKED` is simple, Debezium CDC adds infrastructure.
- **Balance deduction**: single atomic `UPDATE ... WHERE bal >= :x`; `SELECT FOR UPDATE`; optimistic locking with version column; append-only ledger with derived balance; reserve and commit (OCS-style, most complex). Read-modify-write is a lost-update anti-pattern.
- **Rating rules**: tariff rows (queryable, versionable); JSON rules plus a Java strategy per price model; Drools (heavy, hides logic). Rules need effective-from dates. Use `BigDecimal` with fixed rounding.
- **Batch invoicing**: Spring Batch, scheduled partitioned job, or per-account close driven by Kafka. The run must be idempotent per `(account, period)`.
- **Java 21 virtual threads**: fit blocking JDBC and REST. They do not lift connection-pool limits and can pin on `synchronized`. Kafka listener concurrency is still bounded by partitions. (General knowledge, no source opened.)

## Risks

- Scope is large; a thin vertical slice must come first.
- Money correctness: rounding, tier boundaries, time zones at period edges.
- Late and out-of-order events: rating period and correction policy needed.
- Three services add distributed-systems and Testcontainers overhead.
- "Exactly-once" claims are easy to get wrong; say at-least-once plus idempotency.
